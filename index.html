Methodology

Phase 1 starts with a conservative, transparent registry. Track official/core repositories first, verify likely ecosystem repos, and only then expand into discovered community projects.

What's live vs. modeled in this build

The Registry and Repositories tabs' name/URL/category/org-type fields come from an AI-assisted research pass over public GitHub data and may still have rough edges — but a repo's Status badge (Active/Slowing/Stale/Archived/ Unreachable) is computed from real GitHub data wherever the repo is live-ingested, not from that initial research pass. Only the small number of repos outside live ingestion scope fall back to a CSV-recorded status, shown as Unconfirmed unless a human has set something more specific.

Commit/PR/issue/release activity — and star/fork/watcher counts — are ingested daily from the real GitHub API for kaspanet (auto-discovered in full) plus every other registry row with a github.com URL, opt-out rather than opt-in (see Ingestion pipeline below for the exact rule). Those rows carry a ● Live badge in the Repositories tab and heatmap, and a live star count highlighted in green. Rows excluded from live ingestion still show ○ Modeled deterministic placeholder numbers. The Contributors tab uses real commit-author identities (login, avatar, commit count, first/last commit date) for anyone who has committed to an ingested repo, and falls back to placeholder identities only where no ingestion data exists yet at all.

Data Sources

  • • GitHub GraphQL API for structured repo history.
  • • GitHub REST API for commits, PRs, issues, releases.
  • • GitHub Search API for ecosystem discovery.
  • • GitHub Archive / BigQuery for historical backfill.
  • • Community-maintained registry for curation.

Phase 1 Inclusion Rules

  • • Include active public repositories from the primary Kaspa org.
  • • Verify candidate official repos before highlighting them.
  • • Exclude forks, archived repos, and generated repos by default.
  • • Label repos by category: core, wallet, explorer, mining, docs, etc.
  • • Add community repos after manual review.
  • • The CSV's verified/verified_at columns record whether a human has actually checked a specific row against GitHub. They're not shown as a separate public badge — once a repo is live-ingested, its real commit activity is a stronger integrity signal than a one-time manual check — but verified=no still excludes a row from live ingestion entirely (see Ingestion pipeline below).

Metric Definitions

  • • Commits: default-branch commits, excluding obvious bot noise.
  • • Merged PRs: accepted pull requests, stronger signal than opened PRs.
  • • Active developer: author with commit, PR, review, or issue activity.
  • • Releases: published tags/releases from tracked repos.
  • • Registry status: Active, Verify, Slowing, Stale, Deprecated, or Archived.

Ingestion pipeline

A scheduled job (.github/workflows/ingest-activity.yml, running scripts/ingest_github_activity.py) pulls commits, merged PRs, issues, releases, and a stars/forks/watchers/open-issues snapshot once a day for every repo it tracks, buckets the activity into daily aggregates, appends the day's star snapshot to a running per-repo history, and commits the normalized JSON to data/activity/. This UI fetches those files at load time and blends them with modeled data for anything not yet ingested — no backend server required.

Tracked repos: full auto-discovery for accounts in ORGS (currently kaspanet), plus every registry row with a github.com URL — opt-out rather than opt-in. A row is only skipped if its org type is Uncertain or it's explicitly marked verified=no in the registry CSV. New repos also get a bounded backfill of real historical star growth from GitHub's stargazer timestamps, not just a flat count starting today.

The same run publishes a combined release feed — data/feed/releases.json and an RSS-compatible data/feed/releases.xml — across every tracked repo, which powers the "This Week" panel on Overview and can be subscribed to directly.

Needs a Builder

The Overview tab's Needs a Builder panel is computed client-side from the same data as everything else, not curated: for each registry category it looks at repo count (thin categories) and, once a category has live-ingested repos, whether every one of them has gone quiet for 120+ days (stalled categories). Categories with no live data yet fall back to the count signal alone, and the panel's badge says so.

The New builders column in This Week uses the same live contributor data: anyone whose earliest tracked commit landed within the last 14 days gets listed with the repo it was to, plus a New badge on the Contributors tab. This only fires for live-ingested repos — there's no way to detect a "first commit" for a repo that hasn't been ingested yet, so it stays empty rather than guessing.

The Ideas tab is not modeled at all, live or otherwise — it's a direct read of open GitHub issues labeled idea on this dashboard's own repo (see IDEAS_LABEL and resolve_self_repo() in the ingestion script), sorted by 👍 reaction count. It fetches same-origin data/activity/ideas.json rather than calling the GitHub API from the browser, for the same reasons the rest of the site avoids client-side third-party calls — no CSP exception needed, and no unauthenticated per-visitor rate limit to worry about.

Bus Factor Watch and the ⚠ badge on the Repositories tab flag a repo when one contributor authored 85%+ of its identified commits (commits linked to a real GitHub account — bot commits and old unlinked-email commits aren't counted either way), with at least 5 identified commits so a brand-new repo isn't flagged just for being small. Computed per repo from topContributors in each repo's own activity JSON, not from the org-wide contributor list (which is capped to the top 100 overall and could miss who actually dominates a smaller repo). Live-ingested repos only — no modeled guess at who wrote what.

Every contributor and idea-author avatar is a Kaspicon identicon — a deterministic pixel avatar generated from the handle itself, not GitHub's own avatar photo. GitHub always returns an avatar_url even for accounts with no uploaded photo (it just points at GitHub's own generated identicon in that case), so there's no reliable way to tell "real photo" from "GitHub default" and prefer the former — Kaspicon is used consistently instead. If that script hasn't loaded, everything falls back to a plain colored-initials tile — nothing breaks either way.

Build on this data

Every file this dashboard reads is a static, same-origin JSON file with no auth and no rate limit of its own — you can fetch it directly, whether or not you ever touch this UI. Start at data/api/index.json: it's a versioned manifest listing every published resource (per-repo activity, org-wide rollups, the release feed, the idea board, the source registry CSV) with a description and path for each, regenerated every ingestion run. Two of those resources — _summary.json and _stars.json — are pre-aggregated org-wide rollups this dashboard's own frontend deliberately doesn't use (it recomputes everything client-side from raw per-repo data instead, see above), published specifically for anyone who wants the ready-made version instead of summing every repo file themselves.

schemaVersion in the manifest only changes on a breaking change to a resource already listed — pin to it, not to today's exact field list, if you're building something long-lived. No separate license is asserted over the GitHub-derived data itself; it's a mirror of GitHub's public API, subject to GitHub's own Terms of Service (linked in the manifest).

Methodology

Phase 1 starts with a conservative, transparent registry. Track official/core repositories first, verify likely ecosystem repos, and only then expand into discovered community projects.

What's live vs. modeled in this build

The Registry and Repositories tabs (name, URL, category, org type, status, confidence) are sourced from an AI-assisted research pass over public GitHub data and still need manual verification — see each row's confidence badge.

Commit/PR/issue/release activity — and now star/fork/watcher counts — are ingested daily from the real GitHub API for kaspanet (auto-discovered in full) plus the company-affiliated and community-org repos already listed in the registry (e.g. aspectron, kasplex, K-Kluster). Those rows carry a ● Live badge in the Repositories tab and heatmap, and a live star count highlighted in green. Independent-contributor and uncertain-status repos still show ○ Modeled deterministic placeholder numbers until they're added to the ingestion scope. The Contributors tab remains a modeled placeholder in all cases — contributor identities aren't ingested yet.

Data Sources

  • • GitHub GraphQL API for structured repo history.
  • • GitHub REST API for commits, PRs, issues, releases.
  • • GitHub Search API for ecosystem discovery.
  • • GitHub Archive / BigQuery for historical backfill.
  • • Community-maintained registry for curation.

Phase 1 Inclusion Rules

  • • Include active public repositories from the primary Kaspa org.
  • • Verify candidate official repos before highlighting them.
  • • Exclude forks, archived repos, and generated repos by default.
  • • Label repos by category: core, wallet, explorer, mining, docs, etc.
  • • Add community repos after manual review.
  • • "Verified" in the Registry tab means a human checked that specific row against GitHub — set via the CSV's verified/verified_at columns, independent of the AI-research confidence score.

Metric Definitions

  • • Commits: default-branch commits, excluding obvious bot noise.
  • • Merged PRs: accepted pull requests, stronger signal than opened PRs.
  • • Active developer: author with commit, PR, review, or issue activity.
  • • Releases: published tags/releases from tracked repos.
  • • Registry status: Active, Verify, Slowing, Stale, Deprecated, or Archived.

Ingestion pipeline

A scheduled job (.github/workflows/ingest-activity.yml, running scripts/ingest_github_activity.py) pulls commits, merged PRs, issues, releases, and a stars/forks/watchers/open-issues snapshot once a day for every repo it tracks, buckets the activity into daily aggregates, appends the day's star snapshot to a running per-repo history, and commits the normalized JSON to data/activity/. This UI fetches those files at load time and blends them with modeled data for anything not yet ingested — no backend server required.

Tracked repos: full auto-discovery for accounts in ORGS (currently kaspanet), every registry repo individually tagged company-affiliated or community org, plus any row explicitly marked verified=yes in the registry CSV — the mechanism for graduating an independent-contributor repo into live ingestion once someone has actually checked it (edit two CSV columns, no code change needed). New repos also get a bounded backfill of real historical star growth from GitHub's stargazer timestamps, not just a flat count starting today.

The same run publishes a combined release feed — data/feed/releases.json and an RSS-compatible data/feed/releases.xml — across every tracked repo, which powers the "This Week" panel on Overview and can be subscribed to directly.
